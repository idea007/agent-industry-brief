# 行业新闻简报开发原则

本文定义行业新闻简报长期有效的工程原则。具体功能方案可以更细，但客户端、服务端、
内部 Runtime、数据采集和测试代码都应遵守本文。

相关文档：

- [项目 README](../README.md)
- [项目架构](./项目架构.md)
- [设计规范](./设计规范.md)

## 范围与优先级

- 适用于根目录的 `client`、`server`、`fixtures`、`feeds.json` 及相关测试。
- 原则优先级依次为：用户价值、安全与事实正确、状态一致、过程可追踪、开发便利。
- 文档记录稳定边界，不记录临时实现流水账；代码与文档冲突时必须收敛其中一方。
- 当前项目是单用户、单进程 MVP。新增能力不能假装已经具备多租户、分布式调度或生产级恢复能力。

## 核心原则

### 1. 产品可用性优先，内部能力服务于新闻价值

产品首先帮助用户发现、整理和判断行业新闻。Agent Loop、Tool Policy、Eval、Trace 和
Approval 是可靠性机制，不是用户必须理解的卖点。

- 主要信息流坚持一个新闻事件一张主卡；同一事件的多篇报道作为来源证据聚合，不重复占用信息流。
- 卡片优先展示 AI 摘要、重要度、可信度、来源和时间。
- 新闻详情优先采用稳定 Markdown，不用随机排版增加理解成本。
- 内部运行信息放在辅助诊断入口，不挤占主要阅读路径。
- 技术复杂度必须能换来更好的覆盖率、准确性、可恢复性或安全性。

### 2. 证据优先，结论可追溯

情报事实必须引用当前 Run 实际采集到的 Source ID，事实、推断和来源不得混写。
模型输出只是候选结果，只有通过 Schema、来源完整性、引用一致性和 Prompt Injection
检查后才能保存和投递。

新增摘要、评估、排序或研判能力时，必须回答：

- 输入证据来自哪里。
- 哪些内容是事实，哪些内容是推断。
- 用户如何回到原始来源。
- 证据不足时系统如何表达不确定性。

不得为了让页面“看起来有内容”而补写无来源事实。

### 3. 真实优先，演示和降级必须显式

真实服务可用时以服务端持久化数据为准。Mock Model、Fixture 和客户端演示数据只用于
离线开发、固定回归和明确标识的演示模式，不能伪装成真实新闻或真实运行结果。

允许降级，但降级必须可观察：

- 客户端离线时显示明确的未连接空态，不能静默吞掉请求错误或生成模拟新闻。
- 模型降级必须产生 `model.degraded` 或等价结构化事件。
- 数据源抓取失败必须记录来源、错误和回退方式。
- 无法安全完成的 Run 应进入 `failed`；检索和 Eval 都正常完成、模型明确没有合格事件时，
  可以生成带原因和候选统计的诚实空结果，但不能把执行异常或草稿质量失败包装成成功。
- 候选数与最终卡片数必须分开统计；候选来自 `run_documents`，不得用卡片数反推采集量。

### 4. 真实与 Mock 共用一条可靠性链路

真实模型与 Mock 模型、RSS 与 Fixture 只能替换 Adapter 或数据源，不能绕过：

- Run 状态与预算。
- Tool Schema 和 Tool Policy。
- Append-only Event Log。
- Eval 硬门禁。
- Approval Gate。
- 投递流程。

禁止为演示、测试或某个 Provider 增加一条直接生成最终情报的旁路。测试价值来自复用
真实控制面，而不是只复用返回数据格式。代码中可以保留 Harness 命名，但产品文案应
使用“情报服务”“扫描”和“AI 整理”等用户语言。

### 5. 客户端、服务端边界清晰

客户端只通过 REST 和 SSE 使用服务端能力：

- 客户端不得读取 SQLite、Fixture、Feed 配置或服务端环境变量。
- 服务端不得依赖 React 组件、浏览器状态或客户端 Local Storage。
- `client/` 保存 UI、客户端类型、交互状态和站点构建配置。
- `server/` 保存 API、领域模型、内部 Runtime、调度和持久化代码。
- 项目级来源配置和离线样本保留在 `feeds.json` 与 `fixtures/`。
- 自定义关注的自动来源由 `feeds.json` 中的来源组和匹配规则配置；创建预览、工具可见来源与
  实际扫描必须调用同一个来源解析器，不能在 API、客户端或 Runtime 中硬编码人物特例。
- 自动关注画像必须区分对象类型、所属领域和关系距离。观察到的新实体或来源不得自动升级为
  正式检索条件；至少经过跨 Story 重复证据形成候选，并由用户确认后写入一级关系、二级背景
  或自定义来源。屏蔽反馈必须在下一次排序生效，不能只作为界面状态保存。
- 检索层级和详情故事脉络是两个不同读模型：前者围绕关注对象控制采集距离，后者围绕当前
  Story 的主题与事件轴组织核心、相关和周边。不得因为名称相同而复用持久化字段或混淆文案。

跨边界能力必须先形成明确协议，不使用共享文件路径、隐式全局变量或复制粘贴业务逻辑
建立耦合。

### 6. 分层服务于职责，不制造空抽象

当前依赖方向保持为：

```text
Client → HTTP/SSE API
API → Domain / Database / AgentRuntime
AgentRuntime → Model Adapter / ToolRegistry / ToolPolicy / EvalRunner / Database
ToolRegistry → Source Collector / Database
```

各层约束：

- API 层负责协议、校验、错误映射和任务触发，不编排 Agent Loop。
- Runtime 负责编排，不直接写 SQL、不直接实现 RSS 抓取、不拼 Provider 请求。
- Model Adapter 负责模型协议，不决定工具权限和投递权限。
- Tool Registry 负责工具定义与执行，不自行绕过 Policy。
- Database 负责持久化映射，不承载模型决策和页面展示逻辑。

只有边界稳定、确有复用或需要隔离复杂度时才新增抽象。避免无明确领域含义的
`manager`、`helper`、`utils` 或多层转发。

### 7. 数据库是业务状态权威，事件解释过程

Run、Intel、Approval、自定义来源和订阅以服务端数据库为权威数据源。
客户端 Local Storage 只保存设备级偏好和短期缓存，不能成为业务事实来源。

状态表和 Event Log 分工明确：

- `runs` 保存当前状态，支持快速查询和控制。
- `run_events` 以 Run 内稳定 `seq` 记录发生过的事实。
- `tool_calls` 保存工具意图、策略决策、精简结果和错误，不长期重复保存全部候选正文。
- `source_documents` 保存扫描发现的候选新闻最小索引，并按规范化 URL 去重。
- `run_documents` 保存每次 Run 发现、采用、审阅或阻止了哪些候选新闻。
- `intel_events` 保存通过 Eval 的情报和来源快照；不同 Run 的事件通过稳定 `story_id`
  建立报道关系，不改写各自的证据边界。
- 发布时间、事实发生时间和状态有效性是不同概念。较晚发布的预计、传闻或转载如果已经被
  更高可信度的事实兑现、取消或纠正，应通过 Story 状态和关系标为失效并退出默认信息流，
  但继续保留原事件、引用和来源快照以便追溯。
- `approvals` 保存受保护动作及用户决策。

禁止通过修改或删除历史事件“修正”运行轨迹。需要纠正时追加新事件，并更新当前状态。
同一来源、相似标题和共享实体只能作为聚类证据，不能无条件合并；主体动作、关键数字或
时间发生实质变化时应保留为后续进展。

### 8. Schema 先行，契约同步

跨层数据先在服务端 Pydantic 模型中明确，再同步数据库映射、API 输出和客户端类型。

修改 API 字段时必须同步检查：

1. `server/app/domain/models.py`
2. `server/app/persistence/database.py`
3. `client/app/radar-types.ts`
4. `client/app/radar-initial.ts`
5. API 测试和客户端渲染测试

结构化模型输出必须经过 Pydantic 校验。不要依赖散落的字典键、隐式 `Any` 或前端猜测
服务端字段。

### 9. 外部内容始终不可信

RSS、Atom、网页、聚合器跳转和用户自定义来源均是不可信输入。任何外部正文都不能：

- 改写系统 Prompt 或工具策略。
- 请求额外权限或扩大抓取边界。
- 绕过 Source ID 和 Eval。
- 直接作为 HTML 注入页面。
- 触发未声明的网络请求或投递动作。

采集能力必须限制 HTTPS、主机、重定向、内容类型、响应大小和超时。正文提取失败时可
回退 Feed 摘要，但必须保留来源和内容来源类型。Feed 内容与标题相同或短到不足以构成
正文时，客户端只能基于当前事件摘要和可引用事实生成明确标记的多源整理，不能把标题
伪装成新闻正文，也不能为补足长度虚构信息。

### 10. 工具最小授权，敏感动作前置审批

工具能力遵循最小授权：

- 只向模型暴露当前阶段需要的工具。
- 每个工具必须有输入 Schema、调用预算、超时和错误结构。
- `search_sources` 受搜索次数和查询长度限制。
- `deliver_digest` 只能进入已声明渠道。
- 公开预览必须经过 Approval，批准只对当前请求生效。

新增工具时必须同时补齐 Registry、Policy、Event、Eval 影响和测试，不能只增加执行函数。

### 11. 异步任务必须可取消、可对账、可重复触发

Run 创建与执行分离，API 返回后由 Runtime 的异步 Task 推进。长任务必须：

- 周期性检查取消标记。
- 保持明确终态：`completed`、`failed` 或 `cancelled`。
- 进程启动时对账遗留的非终态 Run。
- 为调度和外部触发设计稳定的幂等键。
- 重试创建新 Run 并关联原 Run，不覆盖旧轨迹。

Scheduler、导入、抓取和投递不得假设“只会执行一次”。对外部 I/O 的重试必须区分可重试
错误与永久错误，并受次数和时间预算限制。

### 12. Provider-neutral，差异收敛在 Adapter

Runtime 只依赖 `ResearchModelAdapter` 返回的 `ModelDecision`，不感知 DeepSeek、
OpenAI-compatible 细节或 Mock 步骤。

新增模型 Provider 时：

- 在 Adapter 内处理鉴权、消息格式、Tool Call 解析、错误归一和模型降级。
- 不在 Runtime 中增加 Provider 分支。
- 不把 API Key、原始凭据或完整敏感响应写入事件。
- 用协议级测试覆盖 Tool Call、结构化结果、超时和错误响应。

### 13. 失败结构化，可观察但不泄密

关键边界使用结构化 Run Event 和领域错误表达，日志只用于补充进程级诊断。

事件和日志必须：

- 包含可定位的 Run、Tool、阶段、错误码和 Actor。
- 区分用户可见信息与内部诊断。
- 不输出 API Key、Authorization Header、Cookie、密码或完整敏感响应。
- 不把整篇外部正文重复写入事件。
- 不使用散落的 `print`、`console.log` 代替统一状态和错误反馈。

客户端不得只在控制台记录用户可恢复的错误；应在触发位置提供失败信息和下一步。

### 14. 简洁优先，及时收口

实现应直接表达当前业务，不为想象中的未来预埋复杂框架。功能完成后及时清理：

- 临时分支和调试状态。
- 重复类型和重复格式化函数。
- 已失效的兼容路径。
- CSS 文件尾部重复覆盖的旧样式。
- 只为一次演示存在的硬编码数据。

修改 `globals.css` 时优先找到并收口同一组件的主规则，不继续在文件尾追加同名选择器。
当某个视觉表面持续增长时，再按 Dashboard、Trace、Dialog、Editorial 等稳定边界拆分。

### 15. 命名稳定，领域语义明确

- 目录使用项目既有的 `client`、`server` 和领域分层。
- React 组件使用 `PascalCase`。
- TypeScript 函数和变量使用 `camelCase`。
- Python 模块和函数使用 `snake_case`，类使用 `PascalCase`。
- 常量使用 `UPPER_SNAKE_CASE` 或项目已有的只读语义形式。
- Event 使用稳定的 `domain.action` 命名，例如 `tool.completed`。
- ID 使用领域前缀，例如 `run_`、`event_`、`intel_`。

避免含糊的 `data`、`temp`、`handler`、`manager`、`helper`。只有上下文已经明确时才使用
通用短名称。

### 16. 小步变更，验证与风险匹配

每次改动先明确受影响的边界和最小验证路径。默认进行局部验证，以下变更扩大验证范围：

| 变更类型 | 最小验证 |
| --- | --- |
| 文案、静态样式 | 相关页面检查、Lint |
| 客户端状态和组件 | Lint、生产构建、渲染测试 |
| API 和领域模型 | 服务端测试、客户端类型与演示数据检查 |
| Runtime、Policy、Eval | 完整服务端测试及新增失败路径测试 |
| RSS、网络安全边界 | 真实集成 MockTransport 测试 |
| 数据库 Schema | 初始化、旧数据迁移、幂等和回滚检查 |
| 构建与托管配置 | 客户端生产构建和部署产物检查 |

测试必须覆盖成功路径和最重要的拒绝、失败、取消、重试路径。不要为了覆盖率制造低价值
测试，也不要用手工点击替代可重复的核心控制面测试。

### 17. 文档跟随事实，文字保持清爽

长期边界变化时同步更新 README、项目架构、开发原则或设计规范。专项方案只记录稳定
取舍、风险和验收口径，不复制大段实现代码。

中文文档、注释、日志和页面文案中，汉字与英文字母、汉字与数字之间默认保留空格，例如：

- `扫描 12 个来源`
- `Run 已进入 evaluating 阶段`
- `Source ID 不属于当前 Run`

代码标识、路径、URL、版本号和固定品牌写法保持原样。

## 客户端落地规则

- `RadarDashboard` 负责页面级数据编排，展示组件不自行请求同一份全局数据。
- EventSource、定时器和全局事件监听必须在组件卸载时清理。
- Dialog 和 Drawer 复用 `useModalA11y` 的焦点圈定、Escape、滚动锁定和焦点恢复。
- 服务端不可用时保留最后可信状态或明确演示状态，不制造真假混合数据。
- Local Storage 写入失败不能阻塞核心页面；业务数据仍以 API 为准。
- 新增动态行业色时通过语义 CSS 变量传递，不在组件内扩展一套硬编码色板。
- TypeScript 保持明确类型；跨 API 边界不使用未经校验的任意对象。

## 服务端落地规则

- 新增网络 I/O 优先使用异步接口，不能在 Event Loop 中执行长时间阻塞任务。
- FastAPI Lifespan 负责资源创建和释放；后台 Task、HTTP Client 必须可关闭。
- Route 不直接访问模型 Provider 或实现工具逻辑。
- Runtime 的每个长期步骤都应检查预算、取消和终态。
- 数据库操作集中在 Repository；Schema 变更必须支持已有本地数据库升级。
- 外部错误统一转换为稳定错误码，用户信息简洁，内部信息可诊断。
- `.env.example` 只提供非敏感示例，真实凭据不得提交。

## 交付检查清单

- 最终事实是否都有当前 Run 的 Source ID？
- Mock、Fixture、演示或模型降级是否明确可见？
- 新能力是否仍经过 Policy、Budget、Event、Eval 和 Approval？
- 客户端与服务端是否只通过明确协议通信？
- 是否引入了重复业务状态、重复类型或第二条执行路径？
- 外部内容是否仍被当作不可信输入？
- 异步任务是否可取消、可重试、可对账、可幂等执行？
- 错误是否结构化且没有泄露凭据或完整敏感内容？
- 验证范围是否与改动风险匹配？
- README、架构和规范是否仍与代码一致？
