# 行业新闻简报设计规范

本文定义行业新闻简报长期有效的视觉与交互规则。设计以行业新闻工具的可用性为先，
不把 Agent 运行过程或生成式排版作为产品主视觉。

相关文档：

- [项目架构](./项目架构.md)
- [开发原则](./开发原则.md)
- [项目 README](../README.md)

## 1. 设计目标

产品应给人以下感受：

> 冷静、可信、高效的公开动态工作台；用户可以快速扫读卡片，需要时进入结构稳定的
> 故事工作台核对进展、事实、观点和来源。

界面不是营销官网、Agent 教学面板或 AI 杂志生成器。任何视觉和交互都应优先服务：

1. 选择关注行业或对象。
2. 发现最新公开动态。
3. 快速判断是否重要、是否可信。
4. 阅读 AI 整理结果与原始来源。
5. 管理关注来源和扫描状态。

## 2. 核心原则

1. **新闻优先**：标题、来源、时间、AI 摘要、重要度和可信度构成主要阅读层级。
2. **一事件一卡**：同一现实事件只显示一张主卡，多篇报道进入来源证据层；跨事件的
   趋势报告不混入新闻信息流。
3. **详情稳定**：MVP 使用单列 Markdown 阅读，不根据内容随机更换模板。
4. **证据可达**：事实、AI 判断和原始链接之间始终有清晰路径。
5. **AI 退居幕后**：AI 帮助探测、整理和评估，不用拟人化动效或术语抢占注意力。
6. **状态说人话**：优先使用“扫描中、整理中、已更新、失败”，避免要求用户理解
   Run、Tool、Harness 或 Eval。
7. **密度可扫读**：允许高信息密度，但保持清晰层级、足够点击区域和移动端可用性。
8. **装饰服从内容**：不使用复杂排版掩盖正文、来源或结论质量问题。

## 3. 页面信息架构

### 3.1 顶部区域

顶部只承载高频操作：

- 产品名称。
- 当前扫描状态或上次更新时间。
- 更换行业。
- 立即扫描。
- 低权重的“运行信息”入口。

### 3.2 关注与来源栏

- 展示用户已关注的行业、公司、人物、团队、体育、内容娱乐、产品、技术或事件。
- 明确当前浏览或扫描目标。
- 提供来源策略入口。
- 来源入口显示定向来源数量、AI 检索组数；存在自定义来源时追加其数量。
- 自定义关注创建时默认自动识别类型，同时提供行业、公司、人物、团队、体育、内容娱乐、
  产品、技术和事件的手动选择；创建完成后在关注卡片与来源策略中显示实际类型。
- 自动画像使用“对象类型 + 所属领域”两个维度，例如“小米 SU7 = 产品 / 汽车”、
  “梅西 = 人物 / 体育”；类型决定关系结构，领域决定垂直来源和检索词。用户手动选择的
  类型优先于自动识别，避免把识别结果当成不可修正的事实。
- 产品关注的关键词用于填写产品别名和明确关联主体，不用“汽车”“手机”等宽泛品类词
  代替产品名；候选必须直接提及产品，或同时说明产品与母公司、生态、供应商的关系。
- 来源策略详情展示关注对象画像，并把搜索分成核心检索、相关检索和周边检索。核心围绕
  对象本身，相关覆盖母公司、团队、合作方等一级关系，周边覆盖同集团其他业务、竞品、
  行业政策和生态变化。这里描述的是采集距离，不替代详情中围绕单个 Story 计算的故事脉络。
- 系统从至少两个不同 Story 的重复实体和稳定来源中生成“待确认”候选。候选来源先执行
  受限的公开访问试用，展示采集方式、可识别内容、关注词样本命中、历史采用和可靠度；
  用户确认后才加入后续检索。屏蔽反馈应立即影响排序，界面不得暗示系统会静默扩大范围。

### 3.3 动态信息流

默认顺序：

1. 当前关注和结果数量。
2. 最近一次扫描的候选、入选和未采用数量。
3. 必要的扫描状态或错误提示。
4. 事件或持续故事卡片网格。
5. 自定义来源概览或补充来源入口。

扫描漏斗用于解释“发现了多少”和“最终展示多少”的差异；没有最近 Run 或候选记录时
不显示，不使用推测数字补位。

扫描已完成但没有合格事件时，使用中性的“本次未发现可靠结果”状态，并允许查看过程或
再次扫描；执行异常和草稿质量门禁失败继续使用错误状态，二者不可混用。

信息流不常驻展示“全部、新闻、融资、技术、活动、访谈”筛选栏，避免低频或为零的分类
占用手机首屏。分类作为新闻内容属性保留在每张事件卡和详情中；单个关注的结果显著增多、
确有筛选需求时，再提供紧凑的筛选按钮或下拉入口。

信息流直接展示当前关注的全部动态，不额外提供“变化优先 / 全部动态”阅读模式卡片。卡片按
相关报道中最新的 `published_at` 由近到远排列；来源发布时间缺失或不可解析时回退到
`event_time`。最近扫描产生的新 Story 和实质进展可以使用低权重标签说明，但不折叠较早内容。

首屏不插入营销 Banner、装饰统计、AI 综合研判卡或执行轨迹。

### 3.4 辅助入口

- 故事工作台使用 Dialog 或独立页面。
- 行业和来源管理使用 Dialog。
- 运行信息使用 Drawer。
- 运行信息默认收起，仅用于查看扫描进度、失败原因和诊断数据。

## 4. 事件与持续故事卡片

### 4.1 内容层级

每张卡片按以下顺序展示：

1. 行业与分类。
2. 来源覆盖与发布时间。
3. 事件标题。
4. AI 摘要。
5. 阅读详情入口。

标题使用 AI 基于来源整理的事件标题，摘要使用 `summary`。只有一篇来源时可以在详情中
突出原始新闻标题；不要直接把长原文截断当作摘要。

### 4.2 交互

- 点击卡片内容区域打开新闻详情；卡片内不再单独展示评分区或评分说明按钮。
- Hover 只轻微上移、加深边框或阴影，不旋转、不缩放内容。
- 卡片必须可通过键盘聚焦和打开。
- 摘要默认限制三至四行；元信息保持稳定位置。
- 摘要以下区域使用紧凑间距，评分依据和页脚不通过大段留白与正文争夺注意力。
- 同一事件的交叉来源在详情中呈现，不重复生成外观相同的卡片。
- 多来源卡片显示“报道篇数”和“媒体数”，两者不能直接解释为独立证据数。
- 同一事件出现实质进展时可以形成关联的后续事件，不得为减少卡片而吞掉状态变化。
- 同一 Story 存在多个事件时，卡片显示“持续故事 · N 次进展”，主入口使用“查看故事线”。
- “多看这类 / 少看这类”不占用信息卡片空间，统一放在详情的“调整后续动态”区块。反馈
  明确会调整的主题或实体，只影响后续排序，可以撤销，也不能改写当前事件及历史证据。

### 4.3 指标表达

- 重要度和可信度保留在新闻详情的“为什么值得关注”与“AI 判断”区域，不占用卡片的
  快速扫读空间。
- 重要度以 `0–10` 分表达；可信度同时显示“高可信”“待验证”等文字，不能只使用颜色。
- 分数是辅助判断，不伪装成统计学保证。
- 没有足够依据时宁可显示“待验证”，不要给出虚假的精确度。

## 5. 故事工作台

### 5.1 结构

故事详情按三层稳定层级组织：

1. 顶部行动区先展示当前标题和摘要；摘要下方展示已保存的主来源原始完整正文，直接使用
   来源快照的原语言文本，不翻译、不改写、不做 AI 拼接。全文提取结果或来源直接保存的
   足量完整原帖均可展示；只有标题或短 Feed 摘要时明确提示正文暂未获取，并保留原始页面链接。
   原文之后使用三层故事脉络说明当前新闻在最近窗口中的位置；故事脉络之后依次提供
   “一键全面深挖”“持续追踪”和调查路线。
2. 第二层单独展示“AI 判断”，标题之后只呈现“判断结论”，让用户先读结果，不在这里铺开
   可信度卡片和待确认问题。判断结论正文直接跟随标题，不增加卡片边框、背景或重复的“判断结论”
   标签；事实、重要性说明和 AI 推断不得在多个区块重复出现。
3. 第三层使用“事件内容、为什么值得关注、关键事实、判断依据、来源追溯”五个稳定标签，把
   正文、价值、事实、可信度与验证状态、待确认问题和溯源集中在同一内容工作区。移动端标签
   可横向滚动，并支持左右方向键切换。

深挖运行中必须显示明确状态并禁止对同一故事重复启动。调查路线包括：

- 追最新进展：只看新变化、后续动作与明确时间节点。
- 找官方信源：优先声明、原文、当事方回应和一手资料。
- 看不同观点：并列争议焦点、各方立场和冲突证据。
- 补来龙去脉：回溯起因、关键节点、相关主体和历史背景。

当前新闻的证据边界紧邻“事件信息”之前显示，至少说明正文快照形态、独立证据链、可定位引文、
官方来源和冲突状态，让用户在阅读事实、判断依据与来源前先明确可信范围。证据不足时，深挖入口
使用“深挖并补齐证据”，并明确任务会先寻找完整正文、官方来源和第二条独立证据；不得让用户
误以为系统会基于标题直接扩写结论。

路线卡必须说明会启动可追踪的深挖任务；任务启动或运行中只突出当前路线，其余路线暂时
禁用，不能让用户误以为一次点击只是客户端筛选。

持续追踪设置位于顶部行动区，允许用户填写一个具体待确认问题、选择调查路线与
手动/每天/每周频率，并提供“立即检查更新”。事件卡使用低权重“持续追踪”标签。计划扫描
未开启时必须明确说明自动频率暂不执行且不会调用模型，不能把已保存的频率伪装成正在后台运行。

关注信息流不额外展示整个关注主题的时间线，也不放置把多个 Story 改写成一件事的行业级
“故事进展”总结。Story 必须绑定人物、公司、产品、具体事件等可辨识主体；同一 Story 有
两次及以上实质事件时，直接在信息卡中展示“关键故事线”，按时间列出最近三个节点并进入
完整故事工作台。单事件卡不伪造 Story 时间线。未来的“我的追踪”只汇总用户明确启用的
Story，行业级综合总结应使用“行业简报/主题态势”等独立产品对象。

故事关系图只在 `story_relations` 已有关系且相关 Story 可下钻时出现，必须标记关系类型和
置信度，零关系时完全隐藏。

五个内容标签之后保持“故事关系（有数据时）、相关报道、调整后续动态、标签与整理过程”
的顺序。相关报道继续提供可访问的原文链接，不塞入“来源追溯”标签；来源追溯只说明事实源、
最早采集线索、覆盖范围、当前正文载体和判断边界。

缺少某一类内容时可以省略空列表，但故事标题、摘要和来源不可缺失。
非中文新闻正文优先展示扫描时生成并随来源快照保存的中文译文，明确标注为 AI 译文；
历史记录没有译文时展示已有的中文整理并说明降级状态，不把中文摘要伪装成逐段翻译。
当来源快照只有标题或过短的 Feed 摘要时，不得将其标记为“新闻正文”。详情改为展示
基于本次扫描摘要和已引用关键事实的“多源内容整理”，同时说明关联报道数量；证据仍不足
时展示正文暂缺状态并引导用户打开来源。多源整理只能复述已有证据，不能为增加篇幅补写
未经来源支持的细节。
来源追溯必须区分事实源、首发媒体和当前载体；不能确认时显示“源头待确认”。最早采集
时间只能作为线索，不得直接写成绝对首发。

### 5.2 当前新闻的三层故事脉络

三层故事脉络是原 Story 时间线在详情中的扩展表达，不是首页新增的主题总览。它适用于行业、
公司、人物、体育、内容娱乐、产品、技术和具体事件等全部关注类型：

- 当前关注只限定候选范围，三层关系必须以当前 Story 的具体主题和事件轴为中心；标题同时显示
  关注名称与当前主题，例如“机器人 / 具身智能 · 融资 · 最近 30 天”。接口可请求 7–90 天，
  窗口只控制浏览范围，不强制合并 Story。
- 当前新闻在状态仍有效时属于“核心进展”。如果其中的预计、传闻或时间安排已经被更高可信度的
  后续事实兑现、取消或纠正，当前新闻改为“前情 · 已更新”，后续事实成为核心；原报道继续保留
  来源和历史位置，不因界面纠正而删除。其他 Story 与当前新闻主题相同且处于同一事件轴时归入
  核心，处于相邻事件轴时归入“相关动态”，只提供同主题背景或间接影响时归入“周边影响”；仅
  命中宽泛关注词但缺少主题关联的内容不进入故事脉络。
- 三个层级合并在同一纵向时间流中，所有可见节点统一按事件时间倒序展示，距离当前最近的
  节点位于最上方。核心进展贴近主轴，相关动态缩进一级，周边影响缩进两级；支线只表达与
  当前主题的关联层级，不得暗示某条核心新闻是支线新闻的因果父节点。
- 当前新闻必须高亮；状态已失效时同时展示“这不是最新状态”和可下钻的后续事实，不能继续使用
  “核心进展”暗示旧预测仍然有效。界面应说明关注项用于限定候选范围，三层关系围绕当前新闻
  主题计算，避免让用户误以为这是整个关注项的月度总览。
- 每个关联节点仍对应独立 Story；三层结构不能改写各 Story 的事实、引用、来源或历史归属。
- 当前 Story 有多个 IntelEvent 时，在当前节点内继续展示其精确进展；默认显示最近三条并允许
  展开全部，从而保留原 Story 时间线能力。
- 当前窗口只有一个节点时，回退到原 Story 时间线；同一 Story 也只有一个事件时不伪造时间线。

### 5.3 视觉

- 内容宽度建议 `680px–760px`，避免过长行宽。
- 正文使用清晰的无衬线或稳定中文正文字体，行高不低于 `1.7`。
- 一级标题与正文形成明确层级，不使用报纸式多栏、首字下沉或随机网格。
- 引用块只表达 AI 摘要或来源引用，不作为装饰。
- 代码样式仅用于 Source ID、技术标识或确实存在的代码内容。
- 链接颜色和下划线必须可识别，外部链接明确在新窗口打开。

### 5.4 安全与内容边界

- Markdown 渲染不得执行来源 HTML、脚本或内联事件。
- 不直接使用 `dangerouslySetInnerHTML` 渲染外部正文。
- 事实与 AI 判断分区展示。
- Feed 摘要、提取全文、演示内容应显示来源状态。
- 原文链接始终可发现。

### 5.5 详情操作

详情顶栏保留：

- 行业。
- 分类。
- 内容来源状态。
- 阅读时间。
- 关闭。

故事工作台可以提供：

- 原文链接。
- 由服务端 Story 关系支持的相关故事。
- 深挖当前故事。
- “查看整理过程”诊断入口。

MVP 不提供“换一版”“AI 排版”或随机视觉模板。

## 6. 行业与来源管理

- 首次进入引导用户选择行业，文案强调“关注什么”，不解释内部运行架构。
- 自定义主题应支持名称、关键词和排除词；尚未实现的字段要在产品状态中明确。
- 来源管理同时呈现定向来源、AI 探测和用户自定义来源。
- 定向来源数量与 AI 检索组数使用可切换的详情标签；切换后分别列出来源名称、层级、
  原始链接，或实际配置的检索规则、搜索渠道和动态查询占位说明，数量必须与列表一致。
- 来源详情同时列出核心别名、一级关系、二级背景和待确认候选；候选关系显示证据 Story 数，
  候选来源显示采用 Story 数，分别提供“纳入相关/周边检索”和“添加为定向来源”动作。
- 添加来源时说明支持的链接类型和采集方式。
- 来源不可用时给出原因与恢复方式，不静默消失。
- 来源健康详情同时展示请求、新增、入选和全文提取数量；异常来源优先排列，并说明连续失败、
  近期降级或长时间无新增等已保存状态。没有持久化具体错误时不得编造网络或站点原因。
- URL 可以省略显示，但完整链接应可访问或复制。

## 7. 扫描状态与运行信息

### 7.1 用户状态

主要界面使用：

- 正在连接情报服务。
- 正在扫描。
- 正在整理公开动态。
- 正在深挖故事。
- 已更新。
- 扫描未完成。
- 当前为演示数据。

不同关注可以同时发起扫描。同一关注存在运行中或排队中的扫描时，主操作应显示对应状态
并禁止重复启动；其他关注仍可扫描。达到服务端并发上限后，操作文案使用“加入队列”，
行业标签显示“扫描中”或“排队”，让用户无需进入诊断面板即可理解多任务状态。

已完成扫描的漏斗提供可展开说明，区分最终入选、证据复核、暂缓采用和硬门槛拦截，并展示核心、
相关、周边候选覆盖及完整正文比例。未采用原因只能由相关性、新颖度、重复关系、来源偏好、
正文提取和安全标记等持久化信号派生，不直接暴露内部原因码，也不猜测未记录的模型意图。

### 7.2 诊断信息

运行 Drawer 可以保留模型步骤、工具调用、Token、内部阶段和事件时间线，但应满足：

- 默认不展开。
- 标题使用“扫描详情”或“运行信息”，不突出 Harness。
- 先展示用户目标、状态、耗时和错误，再展示技术事件。
- 技术术语不进入主要卡片和新闻详情。

## 8. 色彩与排版

### 8.1 基础语义色

| Token | 建议值 | 语义 |
| --- | --- | --- |
| `--background` | `#f4f6fa` | 应用背景 |
| `--foreground` | `#1a1d24` | 主文字、主要按钮 |
| `--card` | `#ffffff` | 卡片和控件表面 |
| `--muted` | `#6e7585` | 次要文字 |
| `--border` | `rgba(26, 29, 36, 0.09)` | 默认分割 |
| `--accent` | `#00c896` | 在线、扫描、焦点 |
| `--indigo` | `#6366f1` | AI 整理与评估 |
| `--warning` | `#d98a18` | 待确认、需关注 |
| `--danger` | `#d84d5d` | 失败、危险 |

行业色只用于行业圆点、标签、卡片局部强调和详情小面积边线，不生成大面积高饱和背景。

### 8.2 `4px` 空间网格

- 客户端统一以 `4px` 为基础空间单位。大于 `4px` 的间距、定位距离、控件宽高、最小/
  最大尺寸、网格轨道和圆角必须是 `4px` 的整数倍。
- 推荐优先使用 `4px`、`8px`、`12px`、`16px`、`20px`、`24px`、`32px`、`40px`、
  `44px`、`48px` 和 `64px`，避免为单个组件引入相邻但无语义差异的尺寸。
- 最小触控区域不得因对齐网格而缩小；需要调整时向上取整，例如把 `42px` 调整为
  `44px`。
- `1px–4px` 可用于发丝线、描边、状态点和细微光学校正。字号、无单位行高、媒体查询
  断点、百分比、视口单位和图片固有尺寸不受空间网格约束。
- CSS 空间属性和空间类自定义变量由自动测试检查；新增样式不得通过 `calc()`、负值或
  大圆角常量绕过规则。
- 规则覆盖客户端全部源码样式表和 React 内联样式，而不是只检查主样式文件；生成目录、
  字体包与图片固有尺寸不纳入源码空间网格审计。网格检查接入客户端默认 Lint，不允许带着
  大于 `4px` 的非整数倍空间值通过常规交付验证。

### 8.3 字体层级

- 页面标题：`28px–36px`。
- 卡片标题：`16px–20px`。
- Markdown 一级标题：`30px–42px`。
- Markdown 二级标题：`20px–24px`。
- 正文：`15px–17px`，行高 `1.7–1.85`。
- 元信息：`12px–13px`。

标题可以紧凑，正文必须易读。中文和英文混排时避免过度字距。

### 8.4 中英文与数字混排

- 汉字与英文字母相邻时，中间必须保留一个半角空格，例如 `AI 摘要`、`RSS 来源`、
  `OpenAI 发布`。
- 汉字与阿拉伯数字相邻时，中间必须保留一个半角空格，例如 `15 个来源`、`第 3 次扫描`、
  `重要度 8.8 分`。
- 规则适用于标题、正文、按钮、标签、提示、状态、Markdown 详情以及服务端返回的动态
  新闻内容；连续空格不得用来模拟布局。
- URL、电子邮箱、代码、文件路径、Source ID、检索表达式和不可拆分的产品标识内部不
  插入空格；它们与汉字相邻时，仍应在外部边界保留空格，例如 `v0.131.0 版本`。
- 客户端对动态文本统一执行混排空格规范，并跳过 `code`、`pre`、输入控件和显式标记为
  不处理的技术内容。不得依赖编辑人员逐条修正 AI 输出或外部新闻标题。

## 9. Dialog、Drawer 与反馈

- Dialog 使用 `role="dialog"`、`aria-modal="true"` 和可关联标题。
- 打开后限制焦点，Escape 关闭，关闭后焦点回到触发元素。
- 点击遮罩可以关闭，内容区点击不能透传。
- 长内容只滚动内容区，顶部关闭操作保持可达。
- 移动端 Dialog 可贴底或全屏，正文保持单列。
- Loading 不改变组件外部尺寸。
- 错误靠近触发位置，说明原因与下一步。
- 演示、离线和真实状态不得混淆。

## 10. 响应式与可访问性

主要断点：

| 断点 | 主要变化 |
| --- | --- |
| `980px` | 三列新闻卡转为两列 |
| `720px` | 新闻卡单列，Header 和操作区收敛 |
| `620px` | 详情贴近全屏，减少外边距 |
| `420px` | 操作区纵向排列，主按钮占满可用宽度 |

所有常用操作必须支持键盘；焦点样式清楚；颜色不是唯一状态线索；动效尊重
`prefers-reduced-motion`。手机端优先保证无横向溢出、无文字重叠、无关闭按钮丢失。

## 11. 设计验收清单

- 信息流是否做到一个新闻事件只对应一张主卡？
- 多篇相关报道是否进入来源证据层，并区分报道数、媒体数和事实源？
- 卡片是否使用 AI 摘要，而不是大段原文截断？
- 重要度、可信度、来源和时间是否可扫读？
- 点击卡片后是否进入稳定的 Markdown 单列详情？
- 详情是否明确分开事实、AI 判断和来源？
- 是否移除了随机排版、AI 杂志和“换一版”等 MVP 外操作？
- 用户是否无需理解 Agent 或 Harness 就能完成主要任务？
- 行业选择、来源管理、扫描、空态和失败是否都有清晰反馈？
- 键盘、焦点、对比度和移动端是否通过验收？
